а не для редактора. Всё техническое живёт только здесь и в коде.

ОЦЕНКА КАЖДОЙ ЗАМЕТКИ (сказано пользователем, v1.23). Это правило про ЧАТ,
не про сам документ — в данные хроники ничего из этого не пишется. Как
только заметка доведена до финальной компиляции и добавлена в данные
(запись PEOPLE/LORESHEETS/DOMAINS/CLANS/… или интервью по ней завершено),
дай в ответе разбор с позиции нарративного/стори-дизайнера: что в заметке
получилось хорошо, что слабее, насколько она стыкуется с уже существующим
сеттингом и другими записями хроники — и заверши оценкой по шкале 1–10.
Делай это после каждой добавленной заметки без напоминаний, не только
когда попросят. Замечания из этого разбора учитывай при составлении
следующих раундов интервью и будущих заметок — они рабочий инструмент
для тебя, а не часть документа для игроков.

ДОСТАВКА ИЗМЕНЕНИЙ: ТЕЛЕФОН vs ПК (сказано пользователем, v1.36). Это
тоже правило про ЧАТ и твой рабочий процесс, а не про сам документ.
Рассказчик пишет заметки в основном с телефона — в этот момент связь с
его компьютером (device bridge / приложение Claude на ПК) неактивна.
НЕ пытайся в этом случае сразу залить изменения на устройство или
запушить в репозиторий — это либо тихо не сработает, либо попадёт не
туда. Вместо этого после любой правки данных хроники (и вообще любых
правок этого файла) собирай самодостаточный локальный HTML (bash build.sh,
затем python3 build_preview.py — с v1.42 это отдельная копия без

слоем и переключателем «Вид: Игрок / Мастер», см. §1.3.4) и отдавай её рассказчику файлом для скачивания — он сам
откроет его в браузере и проверит результат оффлайн, без бэкенда.
Заливка изменений на устройство/в репозиторий/публикация на сайт —
только по отдельной явной просьбе рассказчика, когда он сам говорит,
что сейчас за ПК со связанной средой («я на этой среде», «подлей на

С v1.27 у файла два места жизни одновременно:
  (а) исходники в /home/claude/v5/ собираются build.sh в один офлайн-файл

КАРТИНКИ — НОВОЕ ПРАВИЛО ПО УМОЛЧАНИЮ: пользователь присылает файл

Так делали для CITY_MAP.img (v1.27 — фон карты вынесен из base64 в
images/city-map.svg, см. §3.3). Правило v1.8 «спрашивать перед вшиванием
base64» по сути снято этим — сама причина (разбухание файла) больше не
действует, раз картинки не вшиваются, а лежат рядом файлами. Но при
добавлении НОВОЙ картинки к записи всё равно уточни у пользователя её имя/
куда класть, если это не очевидно из контекста.
ВАЖНО: если правишь файлы вручную в этой сессии (не просто дописываешь
данные), после того как пользователь пришлёт новую картинку — она должна
быть реально закоммичена и запушена в репозиторий (просто прописать путь

даёт каждый раз заново в чате — он одноразовый и нигде между сессиями не
хранится (осознанное решение по безопасности, не баг).

1.2 ROADMAP: ПЕРЕХОД НА BACKEND (Firebase) — с v1.29, ЕЩЁ НЕ НАЧАТО

СТАТУС: пользователь планирует со временем уйти с чисто-статичного GitHub
Pages (§1.1) на Firebase (Auth + Firestore + Storage), чтобы получить живое
состояние (не только localStorage в браузере, §6) и разделение видимости
контента (не всё, что видит ГМ, обязано быть видно игрокам). Сначала
пользователь хочет дожать текущий контентный проект — сама миграция это
ОТДЕЛЬНЫЙ будущий этап, к реализации ещё не приступали. Ниже — зафиксированный
бэклог функций, отобранный пользователем явным мультивыбором, чтобы не
потерять его до начала работы.

  1) ИГРОВАЯ МЕХАНИКА (во время сессии)
     · живые листы персонажей — track (§3.1/6) редактируется прямо на
       сайте и хранится в Firestore вместо стартовых значений в файле
     · бросок кубов V5 с логом — общий для стола фид бросков (не только
       локальный док костей, §1 «КОСТИ V5»)
     · заявки на даунтайм — игрок отправляет действие между сессиями,
       ГМ отвечает/резолвит, история сохраняется
     · трекер опыта (XP) — журнал начислений и трат по каждому PCS

  2) ДОСТУП И РОЛИ
     · своя закрытая система логинов: только логин+пароль, БЕЗ e-mail
       (пользователь явно исключил почту — узкий круг игроков)
     · три роли: админ / мастер / игрок; роль игроку назначает и меняет
       только админ (админ — техническая роль, ОТДЕЛЬНАЯ от мастера/ГМ)
     · у каждого игрока — свои листы персонажей и своя история бросков
     · РЕШЕНИЕ ПО ПАРОЛЯМ (важно, зафиксировано в чате): изначально
       пользователь просил, чтобы админ мог «скопировать» текущий пароль
       игрока. Ему объяснили: это требует хранить пароли в открытом виде
       в базе — обычный Firebase Auth так делать не даёт вообще никому
       (хранит только хэши, без исключений для админов). Пользователь
       осознанно выбрал БЕЗОПАСНЫЙ вариант: обычный Firebase Auth, админ
       может мгновенно СБРОСИТЬ пароль игрока (поставить новый), но не
       увидеть/скопировать старый. Это финальное решение для реализации —
       НЕ путать с первоначальной формулировкой «скопировать».

  3) ПРИВАТНОСТЬ КОНТЕНТА (то, чего нельзя сделать в статичном HTML)
     · скрытый контент / туман войны — часть записи (или отдельная
       запись) видна только ГМ и раскрывается игрокам по ходу игры
     · личные шёпоты игроку — ГМ отправляет секретную информацию,
       видимую только одному конкретному игроку, а не всем с доступом
       к документу (сейчас документ видят все игроки целиком, см.
       правило «ДОКУМЕНТ ВИДЯТ ИГРОКИ» в начале файла — с бэкендом это
       правило можно будет смягчить точечно, а не только избеганием тем)

  4) МИР И ПОВЕСТВОВАНИЕ
     · карта связей — уже есть офлайн (граф из RELATIONS/BONDS/открытых
       BOONS/sire, §3.4 «ВАЖНО (v1.21)»); с бэкендом может стать общей
       живой картой, а не пересчётом из статичного файла при каждой сборке
     · трекер репутации фракций — статус игрока у каждой секты/фракции
       отдельно от общего Статуса Камарильи/Анархов (§3.4 COURT/status)

  НЕ ОТДЕЛЬНАЯ ФИЧА, А СЛЕДСТВИЕ: автосинхронизация между устройствами
  реализовывать отдельно не нужно — появится сама, как только данные
  переедут в Firestore и появятся логины (сейчас состояние живёт только в
  localStorage конкретного браузера, §6, и никак не расшаривается).

  ТЕХНИЧЕСКИЙ РИСК НА БУДУЩЕЕ (не решено, решать при старте миграции):
  логин без e-mail обычно реализуют поверх Firebase Auth через «фейковый»

  СТАТУС (обновлено v1.38): фундамент (доступ и роли, п.2 выше) — РЕАЛИЗОВАН,

1.3 АВТОРИЗАЦИЯ (Firebase, с v1.31)
════════════════════════════════════════════════════════════════════════════
РЕАЛИЗОВАНО: логин/пароль без e-mail, три роли (админ/мастер/игрок), админ
сбрасывает пароль игрока (не видит старый). Модель — НЕ обычный Firebase
Auth email/password (см. §1.2 v1.29 — от него отказались, чтобы не включать
платный тариф Blaze ради серверной функции сброса пароля). Вместо этого:

  МЕХАНИЗМ. Анонимная авторизация Firebase (бесплатна, без e-mail) даёт
  каждой вкладке браузера служебный uid — это только «якорь сессии» для
  правил Firestore, сам человек через него не идентифицируется. Проверка
  логин/пароль происходит в правилах Firestore (firestore.rules, лежит
  рядом с исходниками, НЕ часть собранного HTML — вставляется в Firebase
  Console → Firestore → Rules отдельно, руками пользователя): клиент
  считает SHA-256 пароля (crypto.subtle, без соли и без bcrypt/Argon2 —
  это ЗАМЕТНО слабее промышленного хранения паролей, но пользователь
  осознанно выбрал этот вариант ради простоты и нулевой стоимости для
  закрытой группы доверенных игроков, см. чат) и пытается создать документ
  sessions/{uid} с этим хэшем — запись правилами разрешена, ТОЛЬКО если
  хэш совпал с сохранённым в users/{имя}.passwordHash. Роль потом всегда
  вычисляется заново через users/{имя}.role (два прыжка get() в правилах,
  sessionUsername() → myRole() в firestore.rules) — клиент не может
  «заявить» себе роль, только у auth.rules есть последнее слово.

  КОЛЛЕКЦИИ FIRESTORE:
    meta/bootstrap    {done:true} — появляется после первого админа,
                      закрывает возможность создать ещё одного «первого»
    users/{username}  {passwordHash, role:'admin'|'master'|'player',
                      displayName, createdAt} — username = id документа
    sessions/{uid}    {username, passwordHash, createdAt} — по одному на
                      анонимный uid браузера; удаляется при выходе

  ПЕРВЫЙ ЗАПУСК: пока users пуст (нет meta/bootstrap) — вместо формы входа
  показывается «Первый запуск», создающая единственного первого админа
  ТРЕМЯ ПОСЛЕДОВАТЕЛЬНЫМИ записями — users, потом sessions, потом
  meta/bootstrap (НЕ batch(), см. v1.34: правила Firestore проверяют
  каждую запись batch по снимку базы ДО всего пакета, поэтому запись
  sessions/{uid} не видела бы только что созданный в том же batch
  users/{имя} — «Missing or insufficient permissions»). Порядок важен:
  users первым (пока meta/bootstrap ещё нет — иначе его же правило create
  не пропустит), meta/bootstrap последним (закрывает лазейку).
  Дальше новых пользователей заводит только админ через #/admin/users
  (там запись users/{имя} одиночная, не batch — этой проблемы нет).

  ФАЙЛЫ: FIREBASE_CONFIG, bootAuth(), формы входа/бутстрапа, бейдж
  пользователя (#userBadge) и админ-панель (viewAdminUsers(), маршрут
  #/admin/users, ТОЛЬКО для role:'admin' — вне CATS/TOOLS: это техническая
  панель приложения, а не контент хроники, поэтому в общий список
  инструментов рассказчика её не добавляли) — всё в файле p3f_auth.js
  (см. §1 — с v1.33 идёт ПЕРЕД p3e_home.js в сборке; закрывающие
  </script></body></html> — в p3e_home.js, он снова последний). Три
  <script src> с самим SDK — в конце <head>, в p1_head.html.
  Старт движка обёрнут: p3e_home.js больше не вызывает route() напрямую,
  а передаёт весь обычный bootstrap (initDock/initSearch/initSession/route)
  колбэком в bootAuth() — вызывается только ПОСЛЕ успешного входа.
  ЕСЛИ SDK НЕ ЗАГРУЗИЛСЯ (нет сети, блокировщик) — typeof firebase
  остаётся 'undefined', fbApp/fbAuth/fbDb остаются null, bootAuth()
  показывает понятную карточку с ошибкой вместо падения всего скрипта на
  ReferenceError — проверено (см. §10, скриншот shots/authgate_error.png).

  БАГ v1.33 (ПОРЯДОК ФАЙЛОВ, УЖЕ ИСПРАВЛЕН): изначально p3f_auth.js шёл
  ПОСЛЕДНИМ в сборке, а его же bootAuth() вызывался из хвоста p3e_home.js —
  то есть ДО того, как в p3f_auth.js успевала выполниться сама строка

  физическому порядку в файле (в отличие от объявлений function, которые
  хостятся целиком) — поэтому в момент вызова bootAuth() переменная fbAuth
  ВСЕГДА была undefined, и пользователь ВСЕГДА видел карточку «не удалось
  загрузить Firebase», даже при полностью рабочей сети и загруженном SDK

  намекает, но причина была не в этом). Раскрыто пользователем: ошибка

  ТЕСТЫ: Firebase недоступен из песочницы агента (тот же сетевой запрет,

  именно поэтому регресс-тест не поймал баг v1.33 — обходной путь

  входа (и порядок её кода) тестами не покрыта вообще. Обход — это

  ПРАВА: мастер/админ редактирует любой живой лист; игрок — только свой
  (owner совпадает с его логином); остальные видят лист, но без кнопок
  правки (только просмотр) — листы персонажей и так открыты всем ролям в

  запись от любого игрока или мастера технически (см. предупреждение прямо

  записываемого документа доверять нельзя, это дало бы любому игроку

  через Firestore пока нет, только через данные страницы). Это сознательное
  упрощение под модель доверия проекта — закрытая группа друзей, тот же
  подход, что и к паролям без соли (§1.3).

  startPcSyncIfLive()/stopPcSync()/pcSyncWrite() — в НОВОМ файле
  p3g_pcsync.js (собирается между p3f_auth.js и p3e_home.js, см. §1).
  trkGet()/trkSet()/trkInner() в p3c_dice.js научены разделять «живой» PC

  внизу экрана) — не только кнопки в trkInner(). stopPcSync() вызывается в

  отдельного экрана — trkInner() сама показывает «Загрузка живого листа…»
  до первого снимка.

  ИЗВЕСТНОЕ ОГРАНИЧЕНИЕ (мелкое, не тронуто намеренно): «Пробуждение»/

  листа пишет запись в лог броска ДО фактической проверки прав в trkSet() —

  запись в логе для того, кто и так не имел права), чинить не стали ради

1.3.2 КОТЕРИЯ: САМОСТОЯТЕЛЬНЫЕ ЧАРНИКИ (Firestore, с v1.37)

Сказано рассказчиком явно (v1.37). Расширяет §1.3.1: там track живого PCS
редактируется на сайте, но САМУ анкету (клан/секта/дисциплины/…) всё ещё

механизм: игрок заводит персонажа САМ во вкладке Котерия (#/cat/players),
без участия агента вообще, и вся анкета целиком (не только track) живёт в

разных механизмов, не путать при правках).

  рассказчиком явным выбором из двух вариантов): игрок видит и открывает
  ТОЛЬКО свой чарник; мастер получает в Котерии отдельную панель с

  без выбора. Другие игроки друг друга не видят вообще. Это ОБЕСПЕЧЕНО
  правилами Firestore (allow read у match /pcs/{pcId} в firestore.rules),
  не только сокрытием кнопок на клиенте — в отличие от pcstate (§1.3.1),
  здесь owner — часть самого документа и проставляется правилом create
  (request.resource.data.owner == sessionUsername()), значит проверку
  владения можно доверить самим правилам, подделать чужой owner нельзя.

  ПРАВКА: только владелец, БЕЗ исключения для мастера/админа — они могут
  посмотреть чужой лист через панель/общий список, но не изменить его.
  Это НАРОЧНО отличается от §1.3.1 (там мастер/админ правят любой живой
  лист статичных PCS[]) — сказано явно, не унификация ради унификации.

  СХЕМА ДОКУМЕНТА pcs/{автогенерированный id}: owner:'логин' (иммутабельно
  после создания, проверяется правилом update), name, short, clan, sect,
  gen, bp, predator, sire, concept:[[label,text],…], disciplines:[[name,
  dots],…], convictions:[[belief,anchor],…], track:{healthMax,wpMax,
  humanity,hunger} (стартовые/максимумы — как у обычного PCS.track), плюс

  pcstate!): hunger,hMax,hSup,hAgg,wMax,wSup,wAgg,hum,stains — та же форма,
  что раньше жила в pcstate/{id} или в localStorage (см. trkDefault в
  p3c_dice.js), плюс createdAt/updatedAt/updatedBy.

  КАК ЭТО СОВМЕЩЕНО С ДВИЖКОМ ТРЕКЕРОВ (§1.3.1/§6): вместо отдельного
  механизма — расширены те же trkKey()/isLivePc()/canEditLivePc()/
  trkGet()/trkSet()/fillPcSelect() (p3c_dice.js) и isLivePc()/
  canEditLivePc()/pcSyncWrite() (p3g_pcsync.js), чтобы понимать объекты с
  меткой x._liveKind==='pcs' (проставляется в p3h_coterie.js при получении
  снимка коллекции — проверка ИМЕННО по этой метке, не по индексу в
  LIVE_PCS[], потому что при каждом onSnapshot массив LIVE_PCS пересоздаётся
  целиком новыми объектами, и старая ссылка из TRK_OBJ иначе бы «протухла»
  посреди работы). Так все кнопки/дока костей/«Пробуждение»/сброс к
  стартовым и т.п. работают для самостоятельных чарников без дублирования
  кода — единственная реальная разница зашита в canEditLivePc() (владелец-
  только для _liveKind==='pcs') и в pcSyncWrite() (пишет в pcs вместо
  pcstate, с merge:true, чтобы не затирать остальные поля анкеты).

  ПОДПИСКА: в отличие от §1.3.1 (подписка на один документ, живёт только
  пока открыта страница конкретного персонажа), здесь ОДНА подписка на всю
  коллекцию pcs, запущенная один раз при входе (startCoterieSync() —
  вызывается из bootAuth() в p3e_home.js, рядом с initDock/initSearch/
  initSession) и живущая всю сессию, не привязана к странице.
  ВАЖНО, ИСПРАВЛЕНО В v1.40 (было записано неверно и стало настоящим багом
  на живом сайте — см. журнал): правила Firestore НЕ фильтруют список
  построчно сами по себе. Для мастера/админа запрос действительно можно
  не сужать (isMaster() не зависит от resource.data — Firestore допускает
  весь список статически), но для игрока запрос ОБЯЗАН сам добавлять
  .where('owner','==',username) — иначе Firestore не может доказать, что
  КАЖДЫЙ возможный результат запроса удовлетворяет правилу (в коллекции
  есть чужие документы), и отклоняет список целиком, а не просто чужие

1.3.3 РЕГИСТРАЦИЯ ИГРОКОВ (p3f_auth.js, с v1.38)
────────────────────────────────────────────────────────────────────────────
Сказано рассказчиком явно (v1.38): новых игроков больше не заводит админ
руками через #/admin/users — они сами создают себе логин и пароль на
экране входа. Спрошено явно и открыто ПОЛНОСТЬЮ (без кода-приглашения) —
любой человек со ссылкой на сайт может завести себе аккаунт-игрока.

ЧТО ДОБАВЛЕНО: на экране входа (showLoginForm) — ссылка «Ещё нет аккаунта?
Зарегистрироваться», переключающая на новую showRegisterForm (логин,
пароль, повтор пароля). Обе формы переключаются друг в друга без
перезагрузки страницы. Роль всегда жёстко 'player' — форма её вообще не
спрашивает, так что подделать через devtools можно разве что сам POST в
Firestore, а не то, что видно в разметке; правило ниже всё равно
перепроверяет role на сервере, а не верит клиенту.

FIRESTORE-ПРАВИЛО (firestore.rules, users/{username}): в allow create
добавлена третья ветка `|| request.resource.data.role == 'player'` — то
есть создание документа с role:'player' разрешено ЛЮБОЙ вошедшей (хотя бы
анонимно) сессии, без исключений. 'master'/'admin' по-прежнему заводит
только первый бутстрап (первая ветка) или сам админ руками (isAdmin(),
вторая ветка) — самостоятельная форма роль повыше прописать не может,
даже если бы попыталась, потому что правило проверяет её в самой
отправляемой записи, а не то, что показала клиентская форма.

«ЛОГИН УЖЕ ЗАНЯТ» — без отдельного чтения наперёд: правило read на
users/{username} не пускает ещё не вошедшего читать чужую запись, значит
заранее узнать «свободен ли логин» нечем. Вместо этого сама попытка
create — это и есть проверка: если документ с таким id уже существует,
Firestore трактует запись как update (независимо от того, что вызвал
клиент — .set() или .update()), а update требует isAdmin() — то есть
попытка занятым логином сама получит permission-denied, и клиент просто
показывает «попробуй другой логин». Гонки состояний тут нет: Firestore
сам решает create/update по факту существования документа на сервере, а
не по догадке клиента.

ПОСЛЕ РЕГИСТРАЦИИ вход происходит сразу же — showRegisterForm вслед за
users/{u}.set() сама создаёт sessions/{uid} с тем же passwordHash (тот же
шаг, что делает обычный логин), и только затем зовёт общий cb(). Если
первый шаг (создание users/{u}) прошёл, а второй (sessions/{uid}) неудачно
оборвался (сеть моргнула) — аккаунт уже реально создан с нужным паролем,
просто клиент об этом не знает; в этом случае показывается отдельное
сообщение «аккаунт создан, обновите страницу и войдите» вместо «логин
занят», чтобы не запутать игрока лишней попыткой регистрации тем же
логином (которая на этот раз закономерно получит «занят»).

Страница #/admin/users (viewAdminUsers) не убрана — админ по-прежнему
может завести мастера/другого админа, сменить роль, сбросить пароль или
удалить запись; в описании страницы добавлена строка о том, что игроки
теперь регистрируются сами.

Не проверено против реального Firebase (см. оговорку в §1.3.2 выше) —
структура проверена макетом (test_register.py): переключение форм;
валидация логина (только [a-z0-9_]), длины пароля (мин. 4) и совпадения
паролей; попытка занятым логином корректно отклоняется с понятной
ошибкой и остаётся на форме регистрации; успешная регистрация создаёт
запись с role:'player', сразу создаёт сессию и заходит; повторный вход
тем же логином/паролем (как после перезагрузки страницы) отрабатывает
штатно. Реальные правила Firestore нужно проверить на живом сайте после
публикации.

  ЗАГОТОВКИ-ПРИЗРАКИ ЗА ПРЕДЕЛАМИ КЛАНОВ/ДИСЦИПЛИН (var GHOSTS, конец d.js):
  Для CLANS/DISCIPLINES заготовки берутся из CLAN_REF/DISC_REF (справочник
  книги, §7). Для остальных разделов такого справочника нет — вместо него
  GHOSTS{people:[…], places:[…], sects:[…], items:[…], threats:[…],
  loresheets:[…], rituals:[…], predators:[…], merits:[…]} — список имён,
  которые ты САМ упомянул в тексте заметок, но полноценной записи для них
  ещё не завёл.
  ПРАВИЛО (важно — на этом уже дважды спотыкались): при добавлении КАЖДОЙ
  новой заметки перечитывай её на предмет чужих имён собственных не только
  в [[Имя]] и card.name, но и в обычном тексте без вики-разметки — short,
  tag, ячейки таблиц (table.rows), quick, ties. Название бара, района,
  фракции или человека, просто упомянутое в таблице или абзаце БЕЗ [[…]],
  всё равно означает «эта сущность существует в хронике, но не описана» —
  заносить в GHOSTS нужно и такие имена, не дожидаясь, пока пользователь
  сам укажет на пропуск. Раздел определяешь по смыслу (кто-то с
  ролью/сиром/приближённым — people; район/бар/дом — places; Камарилья/
  Анархи и т.п. — sects). Ничего не удаляй из GHOSTS вручную — когда
  появится настоящая запись с тем же name, заготовка сама перестанет
  отображаться (движок сверяется с LINKS).
  ЛОРШИТЫ ОСОБО: в этой хронике лоршит — ВАЖНОЕ СОБЫТИЕ в истории мира или
  города, а не человек и не предмет (явное решение пользователя). Источник
  для GHOSTS.loresheets — датированные события в блоках «История» и
  подобных: если у события уже есть имя/заголовок в тексте — заноси его
  как есть; если событие только подразумевается через безымянную фигуру
  («кто он такой, уже никто не помнит») — заносить нечего, пока у САМОГО
  СОБЫТИЯ (не у фигуры) нет названия. Также LINKS — один общий регистр
  имён на ВСЕ разделы сразу (regLink не различает категории), поэтому имя
  события в LORESHEETS не должно совпадать с именем человека/места из
  другого раздела («Война Гекаты», а не «Геката» — Геката уже отдельная
  заготовка в people и станет отдельной записью с тем же name; так и
  разошлись). Тот же принцип держи в уме и для остальных разделов: два
  разных раздела не должны целиться в одинаковый
  name — тогда LINKS не сможет их различить.

  существующей записью (не только через политику/RELATIONS — см. ниже,

  читатель сам дойдёт от новой заметки к старой по ссылке [[…]]. Это
  отдельно от политических связей через глобальный RELATIONS[] (см.
  politicsHtml/§раздел ниже) — там связь всегда двусторонняя автоматически,
  проверка нужна именно для ручных текстовых ties[].

  ties[] НЕ ПИТАЕТ RELATIONS[] — ЗАВОДИ ОБЕ, ЕСЛИ НУЖНЫ ОБЕ (на этом
  споткнулись ещё раз, ровно на той же Кейт Флэмор, v1.39: добавили
  строку в ties[] Гекаты, решили что связь «готова», а на деле

  Граф связей / Паутина (graphData, #/tool/web) читают ТОЛЬКО RELATIONS[]

  полностью раздельных, никак не связанных друг с другом хранилища одной
  и той же фактически связи). ПРАВИЛО: когда новая связь между двумя
  персонажами/держателем и угодьем и т.п. значима настолько, что должна
  быть видна и в прозе на странице (ties[]), и в «Положении среди
  Сородичей»/Графе связей (RELATIONS[]) — заводи ОБЕ записи, они не
  синхронизируются друг с другом автоматически. Не каждая строка ties[]
  обязана иметь пару в RELATIONS[] (RELATIONS — про структурные типы:
  love/ally/enmity/rival/debt/bond/sire/touch/serve/other, см. REL_TYPES
  в p2_data.html) — но если тип отношения туда укладывается и рассказчик
  наверняка захочет видеть его на графе, не полагайся на то, что ties[]
  это уже покрыл.
  Отображение: на странице раздела (#/cat/<id>) — пунктирная карточка;
  для разделов без kind (clans, disciplines, loresheets, sects, people,
  threats, items) это карточка вида god-card (viewList, ghostCard); для
  разделов kind:'cards' (rituals, predators, merits) — карточка вида
  .card (viewCards, ghostFullCard) в общей сетке с обычными карточками;
  для PLACES (kind:'tree') — отдельно, пунктирной строкой в корне дерева
  локаций (вложенные подзоны внутри конкретного места по-прежнему через
  PLACES[].ghosts, см. выше); для DOMAINS (kind:'map', viewDomains) —
  той же карточкой god-card под картой, в общей сетке со «сфигуренными»
  доменами, но БЕЗ полигона на самой карте (у заготовки нет shape —
  появится, когда у домена будет реальная запись с координатами).
  ВАЖНО: «охотничьи угодья», район/территория, которую кто-то ДЕРЖИТ или
  за которую идёт борьба — это GHOSTS.domains, а не GHOSTS.places, даже
  если по ощущению это «локация». PLACES — это конкретные вложенные точки
  (бар, дом, комната, элизиум), DOMAINS — территория на карте города со
  своим держателем/типом/уровнем угрозы. Не путай эти два раздела при
  заведении новых имён.
  ЛОРШИТЫ — СОРТИРОВКА ПО ХРОНОЛОГИИ (v1.21): раздел #/cat/loresheets
  рендерится не общей viewList(), а отдельной viewLoresheets() (p3a_core.js)
  — настоящие записи (по LORESHEETS[].year) и заготовки-призраки
  (GHOSTS.loresheets, год ищется в справочнике LORE_YEARS, p2_data.html,
  сразу после var GHOSTS) сливаются в ОДИН список и сортируются по году
  вместе, а не «сперва карточки, потом заготовки» как везде. Год неизвестен
  — карточка уходит в конец. Когда у события заводится настоящая запись
  LORESHEETS с полем year, соответствующую строку в LORE_YEARS можно (и
  стоит) убрать — она нужна только для ещё не описанных событий.

  COURT      [{sect:'Камарилья', seats:[{title:'Князь', tier:1..4,
             holder:'Имя' или '' (пусто = вакансия), note:''}]}]
             tier = ряд в иерархии (1 — вершина). Шаблон содержит посты
             Камарильи и Анархов — удаляй/добавляй по хронике.
  BOONS      [{id:'b-…', debtor:'Имя', creditor:'Имя',
             level:'trivial|minor|major|life', status:'open|paid|broken',
             why:'за что', n:номер сессии}]
             Погашение = смена status на месте, запись не удалять.
  BONDS      [{thrall:'кто пьёт', regnant:'чью кровь', level:1..3, note}]
  RELATIONS  [{a:'Имя', b:'Имя', type: ключ REL_TYPES, note:''}]
             REL_TYPES: love ally enmity rival debt bond sire touch serve
             other. Узы, открытые долги, сиры и Якоря в граф добавляются
             САМИ — не дублируй их в RELATIONS.
             ВАЖНО (v1.21): «Граф связей» (#/tool/web, graphData в
             p3d_tools.js) строит узлы и рёбра ТОЛЬКО из RELATIONS/BONDS/
             BOONS(open)/.sire/PCS.convictions — прозу из PEOPLE[].ties
             инструмент не читает вообще. Поэтому при каждом новом факте
             отношений (в интервью личности или в свободном тексте, включая
             ties) добавляй СТРУКТУРНОЕ ребро в RELATIONS тоже — иначе лицо
             физически не появится на графе. Имя без своей записи (только
             GHOSTS) всё равно становится валидным узлом графа — меньше,
             синее, некликабельно, но подписано.
             МАСШТАБ (v1.22): drawWeb (p3d_tools.js) держит «камеру» —
             var WEB_VB={x,y,w,h} — поверх неизменной сцены симуляции
             1000×640; сами координаты узлов/рёбер масштаб не трогает,
             меняется только SVG viewBox. Кнопки +/−/1:1 в углу графа,
             колесо мыши (масштаб к курсору) и перетаскивание пустого фона
             (панорама — срабатывает только когда клик НЕ по узлу, иначе
             это обычное перетаскивание узла) читают и пишут один и тот же
             vb. WEB_VB — module-level переменная, как WEB_OFF: масштаб и
             панорама не сбрасываются при переключении фильтров типа связи
             (viewWeb вызывает drawWeb заново, но WEB_VB тот же объект);
             сбрасывается только кнопкой «1:1» или полной перезагрузкой
             страницы.

3.5 ВРЕМЯ И ЖУРНАЛ
  SESSIONS   [{n:1, date:'', note:'', items:[ … ]}], n — целые, по
             возрастанию, без повторов. Элемент items — либо строка,
             либо объект события:
               {t:'текст с [[ссылками]]',
                status:{who:'Имя', sect:'Камарилья', delta:+1|-1},
                masq:+N|-N,               // шкала Маскарада
                boon:'id из BOONS',       // чип-ссылка на реестр долгов
                bond:'Анна → Граф, 2'}    // чип-подпись; саму ступень
                                          // держи в BONDS
             Любое поле эффекта необязательно; несколько сразу — можно.
  CHRON      [{kind:'night'|'memoriam', when:'Ночь 3' или '1888',
             title:'', text:''}] — порядок в массиве = порядок на экране.
  MASQ       {base:0, levels:[[порог,'Название','описание','#цвет'], …]}
             Это рабочая шкала рассказчика, НЕ правило книги.

5. ССЫЛКИ И ТЕКСТОВАЯ РАЗМЕТКА
════════════════════════════════════════════════════════════════════════════
В любом текстовом поле:
  [[Имя]]  [[Имя|подпись]]   вики-ссылка; резолвится по name/aliases/full
                             всех разделов, названиям инструментов и
                             CHRONICLE.city. Нерезолвленная ссылка рисуется
                             пунктирной плашкой «заметки пока нет» — это
                             допустимая заглушка, но СООБЩИ о ней
                             пользователю в ответе.
  **текст**                  жирный
  пустая строка (\n\n)       новый абзац; одиночный \n — перенос строки
Автокнопки бросков (превращаются в кнопки при рендере):
  «пул 6», «пул 6 / сл. 3»   бросок V5 в доке (Голод берётся из дока)
  «проверка пробуждения»     (любое окончание: проверка/проверку/…)
  «2к10+1», «к6»             обычные кости (к2 к3 к4 к6 к8 к10 к12 к20 к100)
  Не пиши эти шаблоны в прозе, если кнопка не нужна.
Поля-ИМЕНА (holder, debtor, creditor, thrall, regnant, a, b, sire, who,
Якорь в convictions, clan, sect, predator) — простые строки БЕЗ [[ ]].
Ссылка строится сама; совпадение сущностей ищется по name/aliases
(функция same()), поэтому пиши имя так же, как в name, или как alias.

CLAN_REF, DISC_REF, BP_TABLE, RESONANCE, TEMPERAMENT, COMPULSIONS —
данные правил V5, ЖЁСТКО ОГРАНИЧЕННЫЕ ТОЛЬКО ОСНОВНОЙ КНИГОЙ (Vampire:
the Masquerade Corebook, Renegade). У пользователя нет доступа к
дополнениям (Players Guide, Camarilla, Anarch, Chicago by Night,
Cults of the Blood Gods и т.д.) — НЕ добавляй факты оттуда, даже если
они общеизвестны фанатам системы. Отсюда сознательно исключены:
  · кланы вне основной книги (Бану Хаким, Геката, Ласомбра,
    Министерство, Равнос, Салюбри, Цимисх — в корбуке только

  · дисциплина Забвение (Oblivion, клан-носитель Геката из допов) —
    её нет в DISC_REF/RESONANCE.
Проверено построчно по тексту книги (pdftotext) на момент v1.2; если
пользователь пришлёт другую книгу/доп — можно расширять, но явно
спрашивай/фиксируй источник каждого нового факта.
BOON_LEVELS, BOON_STATUS — термины (trivial/minor/major/life boon)
подтверждены по корбуку. REL_TYPES, DOMAIN_KINDS — это НЕ цитаты
правил, а собственные категории приложения для учёта отношений и
локаций хроники; их можно менять свободно под нужды конкретной игры.
Меняй справочники правил только по явной просьбе (хоумрул, эррата,
новый источник). Ключи словарей используются в данных — переименование
ключа ломает записи, которые его используют.
